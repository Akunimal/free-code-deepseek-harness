# DSH First-Run Runtime and Fast Installer

## Goal
Fix the v0.9.2 DSH startup failure, fetch the large DSH runtime on first app start instead of installing it with the desktop app, and reduce end-to-end installation cost without inflating the setup unnecessarily.

## Problem and why
The installed 0.9.2 application shows `El harness no pudo arrancar`: DSH fails five readiness attempts with an empty tail. The intended shell Electron dependency is 44.7.0 (Node 24.21.0), but the actual `release/win-unpacked/FreeCode DeepSeek Harness.exe` and installed executable report Electron 35.7.5 (Node 22.16.0, ABI 133). The installed executable hash exactly matches that generated unpacked artifact. File timestamps show this was a stale pre-fix package: `win-unpacked` was written at 01:17 local and setup at 01:24 local, while the source Electron 44.7.0 fix was committed at 08:24 local. DSH uses `import.meta.main` and declares Node `^22.19.0 || >=24.0.0`, so the old Electron 35 runtime is incompatible and can exit silently.

The follow-up v0.9.2 NSIS smoke exposed a second stale-build failure. Its dialog originated under `D:\Temp\freecode-nsis-smoke-iDBxGk\resources\freecode`, confirming it was the temporary install created by `scripts/verify-nsis-install-layout.mjs`. The screenshot reports the excluded runtime manifest and DSH files as missing. Current TypeScript `src/main/index.ts` has `ensurePackagedHarnessRuntime()` and calls it before preflight, but the packaged `dist/src/main/index.js` and `app.asar` lack that bootstrap and still run the legacy preflight. The earlier direct `electron-builder` invocation did not run `pnpm build`; `apps/shell/package.json`'s `package` script does. `electron-builder.yml` intentionally excludes the DSH runtime and manifest, so shipping stale `dist` makes the old preflight fail every time. The prior 0.9.2 artifacts are therefore not accepted as a valid deliverable.

The setup grew from 304,119,145 bytes (0.9.1) to 526,172,056 bytes (0.9.2); the DSH runtime archive grew from 154,456,550 to 421,091,099 bytes. The previous electron-builder compression was `normal`; the current candidate configuration uses `store`. The 0.9.2 installer was active and doing substantial CPU/I/O for about 18 minutes, then completed; it was not hung. The app remains running and must not be killed or disturbed.

## Scope
The latest installed-app log is a distinct native-loader compatibility regression after the ABI149/runtime-bootstrap fixes. The packaged Electron host is 44.7.0 (Node 24.21.0, ABI149), but DSH's native `node-addon-require-builtin` rejects that Electron fingerprint as `Unsupported/no-context`; its error explicitly lists Electron 43.0.0, 44.0.0, and 45.0.0-alpha.6. Reproduced the exact failure by invoking `require('node-addon-require-builtin').requireBuiltin('internal/modules/esm/loader')` under `ELECTRON_RUN_AS_NODE=1`. Vendored DSH `dsh-app-boot` calls the native addon unconditionally, so `--expose-internals` would not bypass this code path. The DSH desktop workspace already locks Electron 44.0.0, the exact supported stable fingerprint. Local fix: pin shell Electron to exact 44.0.0 (preserving ABI149 if verified) and fail packaging if the actual Electron executable cannot use the DSH native loader; add regression tests so future bumps cannot silently ship an unsupported runtime.
- Trace and fail closed on an Electron/Node mismatch in the actual electron-builder `appOutDir`, not only in `node_modules`; ensure no bad setup/portable artifact is accepted.
- On packaged app first start, download the existing configured GitHub runtime asset into writable per-user app data, verify its digest and runtime manifest, extract safely, validate, and atomically activate it. Do not bundle the DSH payload in the setup. Preserve progress/error/retry behavior so a network failure does not turn into five silent supervisor restarts.
- Stream large downloads to disk instead of holding the complete archive in memory. Keep subsequent starts offline when a validated runtime is already installed; keep update checks and replacement atomic.
- Exclude the DSH payload from setup/portable, but package a tiny compatibility manifest so bootstrap can enforce the minimum DSH version and Electron native-module ABI. Honor the user's explicit request to use `store` (no compression) for faster package/install processing. Measure the resulting artifact against the known 526,172,056-byte 0.9.2 setup before delivery; DSH exclusion is the intended source of the size reduction, while `store` may trade some compression for speed.
- Add a fail-closed `afterPack` check and regression coverage proving the actual `app.asar` main entry contains and invokes the first-run DSH bootstrap before preflight; a stale `dist` must fail packaging even when someone invokes `electron-builder` directly.
- Add regression tests in TDD order and update applicable packaging/runtime gates. Version remains 0.9.2 until the user asks otherwise.

## Headless-window regression follow-up

### Goal and root-cause evidence
Eliminate unintended Windows console windows from FreeCode/DSH-owned headless subprocesses and prevent runtime packaging from silently shipping stale fixes. Never interact with or terminate the user's running app.

Verified in this investigation:
- The active userData DSH runtime is `0.2.1-alpha.1` (Node ABI 149); its `tool-pwsh-persistent/lib/index.js` does **not** contain the locally committed DSH-NODE-17 per-command reassertion of `$PSDefaultParameterValues["Start-Process:WindowStyle"]="Hidden"`. The source fix therefore was not delivered in the separately downloaded runtime. This is a concrete runtime-version/artifact drift and a plausible cause when commands use PowerShell `Start-Process`; it does not prove that every reported flash comes from that API.
- The active `node-pty/lib/windowsPtyAgent.js` **does** contain `{ silent: true, windowsHide: true }` for its ConPTY cleanup-agent `fork()`, so that known PTY-cleanup flash fix was delivered. Do not attribute the current report to that helper without contrary evidence.
- The Windows ConPTY integration test ran against the existing native node-pty binary: a `pwsh` terminal and native Node descendant reported `IsWindowVisible(GetConsoleWindow()) === false`. The earlier source assertion demanding `STARTF_USESHOWWINDOW | SW_HIDE` in `conpty.cc` was invalid; ConPTY attaches through `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`, and the real test did not support shipping that C++ change. Withdraw that assertion and discard the unbuilt exploratory C++ patch. The MSBuild attempt failed with `MSB8040` (Spectre-mitigated libraries unavailable).
- The app's centralized child launcher, `opencode2api`, both Git resolver probes, and the standard DSH subprocess/taskkill/RTK/Caveman/ConPTY helpers already request hidden child windows. An expanded `node:child_process` audit found remaining unhidden helper launches in PTC Python's version probe/worker, sandbox's `spawnSync` runner probes (including Windows ACL), SDK and SSH direct child launches, the web-app browser-opener helper, and optional webworker-packer process. `open-in-app` forwards an optional window policy without a hidden fallback. A further test-tooling audit found two real `pwsh` availability probes in `vitest.config.ts` and `snapshots/session/headless.snapshot.ts` that lacked `windowsHide`; these run during harness test/config evaluation and are a direct source of brief PowerShell flashes when that tooling runs. The web-app source now has a red/green option assertion and the local fix, but generated runtime still needs rebuilding. The `native-command` call sites already mark console helpers hidden; Explorer's visible launch is intentional because it opens the user's requested Explorer window. Linux-only systemd probes, POSIX process inspection, and test-support launchers are not Windows runtime flash sources.
- The deeper whole-vendor audit additionally found raw PowerShell availability probes in `tool-pwsh`, `pwsh-local`, `pwsh-sandbox`, and Windows-ACL test suites; a Windows process-table diagnostic in `scripts/run-gates.ts`; a headless DSH Desktop Host child launch; POSIX login-shell probes; a session-snapshot ACP test-agent launch and its detached fixture child; and Linux-only Landlock probes. Runtime PWSH tool commands do pass through the already-hidden shared subprocess service, and all explicit GUI launches remain intentional. Hide the console wrapper on every diagnostic/test process too; preserve the actual Win32 folder-picker UI and `open-in-app`'s opt-in visible policy.
- A setup rebuild alone cannot deliver DSH code changes: the app excludes `dsh/` and downloads an exact-version, separately packaged runtime on first launch. Any runtime version change requires a matching external asset before that installer can run successfully; stop before remote upload and request fresh authorization.

The exact source of all flashes remains unproven because transient windows disappear before the user can capture them, and no process was probed/stopped. Keep conclusions scoped to verified code-path and artifact evidence.
